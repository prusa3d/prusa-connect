Everything a deployment adds to the server is an instance under `resources`,
keyed by its kind and a name you choose. The same instances can be declared in
the web app, which saves them in `config/config.d/resources.json`.

The setup wizard can declare the three most people need. It declares the
storage only when your file declares none, the history store unless you switch
it off, and the MQTT sink only when you switch it on:

- **A storage** for the files you upload, `storage:local`, of type
  `filesystem`, with the folder in `config.root`. The wizard checks the server
  can write there before it lets you on. See [Storage](../storage.md).
- **A history store** for each printer's charts, events, command log and
  finished transfers, `history:past`, of type `core/sqlite`, with its file and
  how long it keeps a sample in `config.retention.raw`. Past that, samples and
  events are deleted, and the command log and the transfers are kept. `0`
  keeps everything, and no value keeps 48 hours.
- **An MQTT sink** that sends each printer's state to a broker, `sink:mqtt`,
  of type `mqtt`, with the broker's address in `config.url`. The server runs
  no broker of its own: it sends to one you run. See
  [MQTT](../mqtt-overview.md).

```yaml
resources:
  storage:
    local:
      type: filesystem
      config:
        root: ./storage
  history:
    past:
      type: core/sqlite
      config:
        path: config/config.d/history.db
        retention: {raw: 168h}
  sink:
    mqtt:
      type: mqtt
      config:
        url: tcp://broker.local:1883
```

A service module has a memory budget, `service.memory_mib`, in MiB. Leave it
out and the module's recommendation applies, or 128 MiB when it makes none.
`service.on_over_memory` says what the server does when the module passes it:
`stop` (the default) or `warn`. On Windows a `warn` module still stops at the
hard limit of its job, which is the budget plus 25 %. A new `memory_mib`
restarts a running module, because the module learns its budget only at
start. A new `on_over_memory` applies at once, with no restart.
`service.switch_off` sets when the server switches the module off because it
keeps failing: `failures` from 0 to 100, where 0 is never, and `window` from
`1m` to `24h`. A value you leave out follows `core.modules_switch_off`. A new
`switch_off` applies at once, with no restart.
[Extensions](extensions.md#how-much-memory-a-module-may-use) says how the
budgets share the machine's memory. `GET /api/v1/resources/{kind}/{name}`
shows the budget under `status.memory`:

| field | what it says |
|---|---|
| `budget_bytes` | the budget in bytes |
| `budget_source` | who set it: `operator`, `author` or `default` |
| `used_bytes` | what the process uses now. Absent while it does not run, or when the server cannot read it |
| `near_budget` | true from 80 % of the budget |
| `failures_in_window` | how many failures count against the module inside the switch-off window, one hour by default |
| `last_stop` | the last of those failures, with its `result`. Absent when none is inside the window |
| `switch_off_failures` | how many failures inside the window switch the module off. 0 is never |
| `switch_off_window_seconds` | the switch-off window in seconds |
| `switch_off_source` | who set the switch-off: `operator` or `default` |
| `switched_off` | present when the server switched the module off, with the time and the stops that made it |
| `held_until_restart` | true for a module in `config.yaml` that stays off until the server restarts |

The `result` of a stop is `over-memory` with `used_bytes` and `budget_bytes`,
`exited` with the exit `code`, `signal` with the `signal` name, or the result
of a start that failed.

The keys below are the ones every instance block has. What goes under
`config` is the instance type's own, and [Extensions](../extensions.md) lists
it for each type.
