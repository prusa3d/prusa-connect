A credential is what a request carries to say who is asking: a session
cookie the browser holds after a login, or a bearer token a program holds.
Most operations need one. The region below marks the few that are sent
without a token.

This server has two ways to log in. With an identity provider configured,
`begin-login` redirects the browser to it and `complete-login` receives the
browser back with a session cookie. With local accounts, `password-login`
checks the name and password against this server's own store. Either way the
session resolves to a principal, the name the permission graph knows you by.
A bearer token minted from a session resolves to the same principal, limited
to the scopes it carries: `read`, `operate` or `administer`. Administering
accounts and other people's credentials takes `configure_resource` on the
`auth` resource kind. Your own credentials take a session and nothing more.
An app can ask a person for a token with a short code instead. See
[scoped credentials and app pairing](../../scoped-credentials-and-app-pairing.md).

A program sends its token as `Authorization: Bearer <token>`. A program
that cannot set that header, such as PrusaSlicer 2 talking to a PrusaLink
printer, sends the same token as `X-Api-Key: <token>`. The server reads it
only for a token it minted itself, and a bearer header wins when a request
carries both
([ADR-20261119-w4q](../../../../../decisions/20261119-w4q-a-credential-this-server-minted-also-travels-in-x-api-key.md)).

## Which operation to call {#which-operation}

| you want to | call |
|---|---|
| know which login form to show | [`get-auth-info`](#get-auth-info) |
| create the first administrator on a new server | [`create-first-account`](#create-first-account) |
| sign in | [`begin-login`](#begin-login) and [`complete-login`](#complete-login), or [`password-login`](#password-login) |
| give a program a token | [`create-credential`](#create-credential) |
| see, or take back, the tokens a principal holds | [`list-credentials`](#list-credentials), [`revoke-credential`](#revoke-credential) |
| let an app ask a person for a token | [`request-app-pairing`](#request-app-pairing), then [`collect-app-pairing`](#collect-app-pairing) |
| read and decide what an app asks for | [`get-app-pairing`](#get-app-pairing), [`approve-app-pairing`](#approve-app-pairing), [`deny-app-pairing`](#deny-app-pairing) |
| end the session this request carries | [`logout`](#logout) |
| add, list or remove people | [`create-account`](#create-account), [`list-accounts`](#list-accounts), [`delete-account`](#delete-account) |
| change a password, or reset somebody's | [`set-account-password`](#set-account-password) |

The token appears once, in the answer to `create-credential`. The server
keeps a hash and lists the credential afterwards with no token in it. Keep
it out of your source, and revoke it when it leaks.

### `approve-app-pairing` {#approve-app-pairing}

`POST /api/v1/auth/app-pairings/{user_code}/approve`. Approve a pairing.

Gives the app a credential that speaks for you, limited to the scopes approved: the ones it asked for or fewer. The credential never reaches more than you do, it lives ninety days, and it is listed with your credentials, where you revoke it. It takes a sign-in as a person, so an api credential cannot approve one.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `user_code` | path | `string` | yes | The code the app shows, with or without the dash, in any case. |

- credential: bearer token. The client method is `approveAppPairing`
- request body: `application/json` (`ApproveAppPairingBody`), optional
- response `204`: No Content, no body
- errors: `401`, `403`, `404`, `409`, `422`, `500`, each a [problem document](../../error-codes.md)

This operation has no sample: 204. The credential goes to the app on its next poll, and the person's listing is where it shows.

### `begin-login` {#begin-login}

`GET /api/v1/auth/login`. Start a login.

Redirects to the configured issuer with a fresh state, nonce and PKCE challenge. The verifier stays on this server, which is what binds the callback to the request that started it. A deployment with no issuer refuses here rather than admitting the caller.

- credential: none, the request is sent without a token. The client method is `beginLogin`
- request body: none
- errors: `303`, `401`, `500`, each a [problem document](../../error-codes.md)

This operation has no sample: 303 to the issuer. The body is empty and the answer is the Location header.

### `collect-app-pairing` {#collect-app-pairing}

### `complete-login` {#complete-login}

`GET /api/v1/auth/callback`. Finish a login.

Exchanges the issuer's authorization code, checks the ID token against the login that started it, and sets the session credential as an HttpOnly cookie. The issuer's own tokens are not kept and are never presented anywhere. A login this server started that fails, because the issuer refused it or its ID token or subject was refused here, returns the browser to `/?sign_in_error=&lt;reason>` with the cookie expired, and the log says why. A callback for a login this server did not start answers 401.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `state` | query | `string` | no | The value this server minted when the login began. |
| `code` | query | `string` | no | The authorization code to exchange. |
| `error` | query | `string` | no | The error the issuer refused the login with, RFC 6749 section 4.1.2.1. |

- credential: none, the request is sent without a token. The client method is `completeLogin`
- request body: none
- errors: `303`, `401`, `422`, `500`, each a [problem document](../../error-codes.md)

This operation has no sample: 303 back to the application, with the session in a Set-Cookie header.

### `create-account` {#create-account}

`POST /api/v1/auth/accounts`. Add a person.

Creates an account under a minted id. Without a role the id holds no grant, so the new person can log in and can do nothing until one is written for them; with a role the role is written in the same call, so one request produces a usable person. The answer carries the subject in tuple spelling, which is what a grant names. It takes configure_resource on the auth resource kind, and the role is written as set-account-role writes it, so any role that call accepts is accepted here, admin included. It also takes a sign-in, which is a session or a Prusa Account token that a pairing names a person with. An api credential, and a token paired to a service account, are refused with SESSION_REQUIRED.

- credential: bearer token. The client method is `createAccount`
- request body: `application/json` (`AccountBody`), required
- response `201`: Created, `application/json` (`Account`)

### `create-credential` {#create-credential}

`POST /api/v1/auth/credentials`. Mint an api credential.

Mints a bearer token and returns it once; this server keeps only a hash of it. It is accepted wherever a session is on the HTTP surface and resolves to the same principal, with the same grants. A mint takes a sign-in, which is a session or a Prusa Account token that a pairing names a person with. An api credential cannot mint another one, and neither can a token paired to a service account. The expiry is at most 365 days away. Your own takes no grant beyond being signed in. One for another person or for a service account takes configure_resource on the auth resource kind, which is what administering this server's identity means in the graph. The scopes limit what the credential may use of the principal's grants: read observes, operate also acts on printers and writes files, administer allows every grant the principal holds. A credential never reaches more than its principal does. Empty scopes take read.

- credential: bearer token. The client method is `createCredential`
- request body: `application/json` (`CredentialBody`), required
- response `201`: Created, `application/json` (`CreatedCredentialBody`)
- errors: `401`, `403`, `422`, `500`, each a [problem document](../../error-codes.md)

#### Sample {#sample-create-credential}

```sh
curl -X POST "http://127.0.0.1:8080/api/v1/auth/credentials" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "nightly export",
    "scopes": [
      "read"
    ]
  }'
```

