A camera is a video device an operator declared under
[resources](./resources.md) and pointed at a printer. This page is about
what the camera sees. Its declaration, and whether it is running, are on the
resources page.

A camera instance captures frames on its own cadence, and each new still is
published as `com.prusa.connect.camera.snapshot.captured` on the event
stream. A camera sits under the same grant as the printer it watches. A
caller who may read the printer's telemetry may see its camera, and one who
may not is not told the camera exists. The server keeps the newest still and
serves it as a JPEG. For a live view it relays the camera's own frames
without decoding them, as a multipart stream an `img` tag plays, or over
WebRTC for an H.264 camera. A build wired with no media plane serves none
of these paths.

## Which operation to call {#which-operation}

| you want to | call |
|---|---|
| show a thumbnail, refreshed on the camera's cadence | [`get-camera-snapshot`](#get-camera-snapshot), with `If-Modified-Since` |
| list the cameras, or the ones on one printer | [`list-cameras`](#list-cameras), with `device` |
| play a live view in an `img` tag | [`stream-camera`](#stream-camera) |
| play an H.264 camera in a browser | [`watch-camera`](#watch-camera) |

A stream is an endless body. Open one per view a person is looking at and
close it when they leave. A reverse proxy that buffers responses holds the
whole body and delivers nothing, and the response carries
`X-Accel-Buffering: no` to tell it not to.

### `get-camera-snapshot` {#get-camera-snapshot}

`GET /api/v1/cameras/{camera}/snapshot`. One camera's most recent still image.

Answers image/jpeg, with Last-Modified and a private max-age of the camera's own cadence. A client that sends If-Modified-Since is answered 304 with no body while its copy is current, which is how a grid of four hundred printers costs four hundred empty responses rather than four hundred images. A camera that is working and has produced no frame yet answers 204. Cache-Control is private, so a shared proxy never holds one caller's frame and serves it to another. A camera this server could not read answers 502, and a retry may work: the request is correct and the device did not answer.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `camera` | path | `string` | yes | The camera's name. |
| `If-Modified-Since` | header | `string` | no | The Last-Modified of the frame this client already has. A frame no newer than it answers 304 with no body, which is what makes a grid of four hundred thumbnails cheap. |

- credential: bearer token. The client method is `getCameraSnapshot`

### `live-camera` {#live-camera}

`GET /api/v1/cameras/{camera}/live`. One camera's live view over a websocket.

Upgrades to a websocket that carries the camera's H.264 stream, for a browser that cannot reach this server over WebRTC: behind a tunnel that carries no UDP, or a container with no published UDP port. Each binary message is one picture: a flag byte, 1 for a keyframe and 0 otherwise, then the access unit in Annex-B framing. The first message is a keyframe, and every keyframe carries the parameter sets. A viewer that falls about a second behind skips to the next keyframe. Nothing is decoded or re-encoded. A camera that emits no H.264 answers 404, the same refusal as one the caller may not see.

### `put-camera-snapshot` {#put-camera-snapshot}

`PUT /api/v1/cameras/{camera}/snapshot`. Send one frame from a camera that cannot be read.

Takes one JPEG as image/jpeg, at most 8 MiB, and stores it as this camera's most recent frame. It is for a camera this server cannot dial: the device sends its own picture, and the snapshot and stream paths then serve it exactly as they serve a frame the server fetched. Nothing is decoded or converted, so a body that is not a JPEG is refused rather than re-encoded.

It takes operate on the camera, which a viewer does not hold: whoever may watch a camera must not be able to decide what it shows. A camera the caller may not see, one that is not declared, and one whose driver reads a device rather than taking frames all answer 404, which is the same refusal the rest of this surface gives.

The answer is 204 and carries no body. When the frame was taken is this server's own clock and not the device's, because a camera whose clock is a year out would be a thumbnail no conditional request ever refreshes.

### `watch-camera` {#watch-camera}

`POST /api/v1/cameras/{camera}/webrtc`. One camera's live view over WebRTC.

Takes an SDP offer as application/sdp and answers with an SDP answer that already carries every ICE candidate, so one request completes the negotiation. It is how an H.264 camera is watched in a browser: the elementary stream is repacketised into RTP and nothing is decoded or re-encoded. The server offers no ICE server of its own, because host candidates are enough on the network the camera is on. A camera that emits no H.264 answers 404, the same refusal as one the caller may not see.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `camera` | path | `string` | yes | The camera's name. |

- credential: bearer token. The client method is `watchCamera`
- request body: `application/octet-stream` (`binary`) or `application/sdp` (`string`), required
- response `201`: The SDP answer, with the ICE candidates already gathered into it, `application/sdp` (`string`)
- errors: `400`, `401`, `404`, `422`, `429`, `500`, `502`, each a [problem document](../../error-codes.md)
