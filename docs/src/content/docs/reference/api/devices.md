A device is a printer that dialled in to this server. Nothing in the
configuration file creates one. The printer introduces itself over its own
connection and somebody admits it, or the connector admits it on arrival.
From then on it is a device with an id, a kind and a capability set. The
server keeps the last state the printer reported and answers every read
below from that copy, so a read never waits on the machine. A command goes
the other way: the server checks it against the capability set it resolved
for that printer and sends it down the same connection.

The `device_id` every path takes is the identity the listing reports. A
printer whose session has ended stays listed, with its last state and a
`departed` member saying why it went. So a machine that was here reads
differently from an id the server never met.

Every operation checks what the caller holds on that one device. A read
takes `observe`, and anything that changes what the machine is doing takes
`operate`. Each section below says which it takes. A refusal is a problem
document whose `code` names the missing action, and the
[error codes](../../error-codes.md) page says what to do about each one.

## Which operation to call {#which-operation}

| you want to | call |

| show one printer: what it is, what it can do, what it reported | [`get-device`](#get-device) |
| see the print running now and the one before it | [`get-device-jobs`](#get-device-jobs) |
| scroll the prints a machine has finished | [`list-device-jobs`](#list-device-jobs), paged by its `cursor` |

| start, pause, cancel, home, or set a temperature | [`send-device-command`](#send-device-command), with a verb from the capability set |
| browse a printer's storage | [`list-device-storages`](#list-device-storages), then [`list-device-files`](#list-device-files) |
| put a file on the printer, or take one off | [`send-device-file`](#send-device-file), [`delete-device-file`](#delete-device-file) |
| make or remove a folder | [`create-device-folder`](#create-device-folder), [`delete-device-folder`](#delete-device-folder) |
| watch or stop a file the server is sending | [`list-device-transfers`](#list-device-transfers), [`stop-device-transfer`](#stop-device-transfer) |
| tag a machine in your own words | [`set-device-tags`](#set-device-tags) |
| call a machine something a person recognises | [`set-device-name`](#set-device-name) |
| take a machine you no longer have off the fleet | [`retire-device`](#retire-device) |
| run gcode the capability model cannot check | [`send-printer-gcode`](#send-printer-gcode) |
| keep gcode you run often, and run it by name | [`put-gcode-preset`](#put-gcode-preset), then [`run-printer-gcode-preset`](#run-printer-gcode-preset) |

Send a command before you send gcode. The server checks a command's verb
and its arguments against what the printer can do and refuses what it
cannot check. Raw gcode is the one payload it cannot read, so it takes a
grant an operator does not hold. The run stops at the first line the
printer refuses, and nothing that ran is undone.

### `get-device-file-thumbnail` {#get-device-file-thumbnail}

`GET /api/v1/devices/{device_id}/files/thumbnail`. The picture inside one file on a printer.

Serves the thumbnail the printer reads out of a .gcode or .bgcode file on its own storage, as image/png or image/jpeg. The printer is asked for it unless the request names the version of the file with size and modified and this server already holds the picture for that version. After a listing comes from the printer, and unless core.device_thumbnail_prefetch is off, this server asks it for the picture of each listed print file, one file at a time and only while the printer is idle, so such a request usually finds the picture held. A version that carries no picture is remembered as well. Unless core.device_thumbnail_disk is off, both are kept on disk too, so a restart does not ask the printer again. It carries an ETag taken from the file's size and modification time, and a client that sends it back in If-None-Match is answered 304 with no body. Cache-Control is private, no-cache. A file that carries no picture, and a folder, answer 404 with core.storage/NO_THUMBNAIL. It takes operate on the printer, because answering it can put a frame on the wire.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `device_id` | path | `string` | yes | The device's identity, as the listing reports it. |
| `path` | query | `string` | yes | The storage-prefixed print file, such as usb/part.bgcode. |
| `size` | query | `integer` | no | The file's size as the listing reported it. With modified, it names the version of the file, and a picture this server holds for that version is served without asking the printer. Absent or zero always asks. |
| `modified` | query | `integer` | no | The file's modification time as the listing reported it, in seconds since the Unix epoch. Zero is a printer that reported none. |
| `If-None-Match` | header | `string` | no | The entity tag of the picture this client already has. A picture with the same tag answers 304 with no body. |

- credential: bearer token. The client method is `getDeviceFileThumbnail`
- request body: none
- response `200`: The picture stored inside the file, `image/jpeg` (`binary`) or `image/png` (`binary`)
- errors: `304`, `400`, `401`, `403`, `404`, `409`, `422`, `500`, each a [problem document](../../error-codes.md)

This operation has no sample: one PNG or JPEG picture, for the same reason the camera's still image is.

### `get-device-jobs` {#get-device-jobs}

`GET /api/v1/devices/{device_id}/jobs`. The print on a device and the one before it.

What the machine is printing now and what it printed last, from the record store rather than from the live session. So a print survives a restart of this server: the row was written as the machine reported it and is read back here whether or not the machine is connected.

`current` is the print on the bed and is absent when there is none. `last` is the most recent print that ended, and the two are never the same row. A print's `state` is the machine's own word for what it is doing, from the vocabulary the device kind declares, so read it as an open value.

It takes observe on the device, which is what `GET /api/v1/devices/{device_id}` takes: a job is a reading about a machine. A device the caller reaches nothing on and an id this server has never been dialled by are the same 404.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `device_id` | path | `string` | yes | The device's identity, as the listing reports it. |

- credential: bearer token. The client method is `getDeviceJobs`
- request body: none
- response `200`: OK, `application/json` (`DeviceJobs`)
- errors: `401`, `403`, `404`, `422`, `500`, each a [problem document](../../error-codes.md)

### `list-device-files` {#list-device-files}

`GET /api/v1/devices/{device_id}/files`. One directory of a printer's file tree.

### `list-device-jobs` {#list-device-jobs}

### `list-devices` {#list-devices}

`GET /api/v1/devices`. The devices this caller may see.

Every printer that has dialled in and that the caller holds observe on. A printer appears here when it is admitted, not when it is configured: nothing in the configuration file names one. A printer whose session has ended stays on the list, carrying the last state it reported and a `departed` member saying why it went, so a machine that was here reads differently from an id that never answered. The answer is one page: it carries the total over every page and the limit and offset that were applied, so a fleet larger than one page is walked with the offset parameter rather than truncated.

Every printer carries an `issues` array saying what this server has found wrong with it, worst first, and the page carries the rollup of those issues over every printer the caller may see. So one request is enough to load a fleet page and say which machines need somebody. `with_issues=true` narrows the page to those machines. The reasons are a closed set published at `/api/v1/vocabularies/device-issues`, which carries the sentence and what to do about each one.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `limit` | query | `integer` | no | How many printers to return. Omitted or zero is the server's default page size. A value above the server's cap is answered with the cap, and the answer says which limit was applied. |
| `offset` | query | `integer` | no | How many printers to skip. The order is stable across pages, so paging by offset walks the fleet exactly once. |
| `with_issues` | query | `boolean` | no | Return only the printers carrying at least one issue. It narrows items and total; the issues rollup stays over every printer this caller may see, so a client filtering to the problems still knows how large the fleet behind them is. |
| `tag` | query | `array or null` | no | Return only the devices carrying every one of these tags, comma separated. The match is on the whole tag and ignores case, joiners and emoji selectors, so petg only finds PETG only. It narrows items and total and never the issues rollup, and it can only narrow: a tag decides no permission. |
| `labels` | query | `array or null` | no | Deprecated. The tag filter spelled as labels, each key or key=value, comma separated. key=value finds the tag key: value, and a bare key finds the tag key or any tag that starts with key and a colon. A term that is not a valid label key or value is refused. Use tag instead. This parameter is removed in a later release. |

### `list-jobs` {#list-jobs}

`GET /api/v1/jobs`. The prints across the fleet.

A page of the prints on every device the caller may observe, running and ended, newest start first. It is what a jobs page reads: one request for the whole farm, where the device routes answer one printer at a time.

`phase` narrows the page to the prints still on the bed or to the ones that have ended, and `device_id` narrows it to one device. A print is running while it has no `ended`.

`from` and `to` narrow the page to the prints that ended inside a range of time, which is what a report over the fleet reads. Either one alone bounds that end only. A `from` after a `to` is refused, and so is either one with `phase` running, because a running print has not ended.

Paging follows the `cursor` member: send it back as the `cursor` parameter for the next page, and stop when it comes back empty. The rows are read from the record store, so they survive a restart of this server.

It takes observe on each device, which is what the jobs read takes. The permission is resolved inside the query, so a device the caller reaches nothing on adds no row and moves no cursor, and naming it in `device_id` answers an empty page and not a refusal.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `device_id` | query | `string` | no | Only the prints of this device. A device the caller may not observe answers an empty page, exactly as one that has never printed does, so the answer never says whether a device exists. Omitted is every device the caller may observe. |
| `phase` | query | `one of running, ended` | no | Only the prints still on the bed, or only the prints that have ended. Omitted is both. |
| `from` | query | `string` | no | Only prints that ended at or after this instant, as RFC 3339. It narrows the page to the prints that have ended, so it cannot be sent with phase running. Omitted is no lower bound. |
| `to` | query | `string` | no | Only prints that ended at or before this instant, as RFC 3339. It narrows the page to the prints that have ended, so it cannot be sent with phase running. Omitted is no upper bound. |
| `limit` | query | `integer` | no | How many prints to return. Omitted or zero is the server's default page size, and a value above the cap is answered with the cap. |
| `cursor` | query | `string` | no | The cursor a previous page returned. It is minted by this server and its form is not part of this contract. |

- credential: bearer token. The client method is `listJobs`
- request body: none
- response `200`: OK, `application/json` (`JobPage`)
- errors: `400`, `422`, `500`, each a [problem document](../../error-codes.md)

### `print-device-file` {#print-device-file}

`POST /api/v1/devices/{device_id}/print`. Print a file on a printer.

Starts a print in one call. Name `path` alone to print a file the machine already holds. Name `storage` and `source` as well to print a file one of this deployment's storages holds: the file is relayed to the machine first and `path` is where it lands, so a page that has just uploaded a file prints it without calling send-device-file and send-device-command itself.

A printer refuses a file sent to a name it already holds. When this server sent that same version of the stored file there since it started, and the printer's copy has not changed since, that copy is printed and nothing is sent. Any other file there is refused with core.printer/FILE_NAME_TAKEN, and the request sent again with `replace` true deletes it and sends this one.

It returns when the printer has answered the start command, so with a storage it takes as long as the transfer does. A client that stops waiting stops neither the transfer nor the start command that follows it. A printer that refuses the command answers 200 with `command.ok` false, the way send-device-command does, and the transfer that already happened is reported beside it. A path carrying a .. segment is refused here and never reaches the printer.

It takes operate on the printer, and read_storage on the storage kind when a storage is named.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `device_id` | path | `string` | yes | The device's identity, as the listing reports it. |

- credential: bearer token. The client method is `printDeviceFile`
- request body: `application/json` (`DevicePrint`), required
- response `200`: OK, `application/json` (`DevicePrintResult`)
- errors: `400`, `401`, `403`, `404`, `409`, `422`, `500`, each a [problem document](../../error-codes.md)
