The system operations say how this process is doing. They say whether it is
up, whether it should receive traffic, who it thinks you are, how its printers
are faring and what it is measuring. A load balancer, a monitoring stack and
a client's first request read them.

Two probes take no credential, because the process that reads them cannot
hold one. Liveness says the process is serving and reads nothing else.
Readiness is 200 while every instance the configuration marks required is
serving, and 503 while one is not. An optional resource never makes the
process unready, so a failing sink cannot take the printer path out of
service. Printer health is deliberately outside readiness: a printer
switched off overnight is normal, and a probe that failed for it would take
a healthy process out of rotation. The metrics exposition is one document
over the whole fleet, so reading it takes telemetry on every device this
server has seen.

Liveness also names this server. `instance_id` is a random id the server
writes into its database on the first start. It stays the same after a
restart, an upgrade or a new address, and a second install has a different
one. A client that found the server on the network reads it before it signs
in, and knows the server again when its address changes. The mDNS record
carries the same id, as [discovery on the local network](../../config/discovery.md#what-the-record-says)
explains.

## Which operation to call {#which-operation}

| you want to | call |
|---|---|
| a Kubernetes or Docker liveness probe | [`get-health`](#get-health) |
| a readiness probe, or a gate in front of traffic | [`get-readiness`](#get-readiness) |
| check which principal your token resolved to before acting | [`get-principal`](#get-principal) |
| show printer health rolled up per connector, worst first | [`get-connector-health`](#get-connector-health) |
| scrape Prometheus metrics | [`get-metrics`](#get-metrics) |

A build compiled without the observability tag answers 404 at `/metrics`. It
is a scrape target that says it has nothing, and not a healthy process with
no series.

### `create-diagnostics-bundle` {#create-diagnostics-bundle}

`POST /api/v1/diagnostics`. A redacted diagnostics bundle.

Builds a zip of recent logs, the last crash and the shape of this install, with secrets and personal data removed, for an operator to attach to a support ticket. The body is the browser's own error buffer, an empty array when it holds nothing; an unreadable one is left out of the bundle rather than refused. Nothing is stored. One bundle is built at a time, and a request while one is in progress answers 429.

It takes the admin role on the organization, because the bundle describes the whole server.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `modules` | query | `boolean` | no | Include what modules wrote to standard error, scrubbed. Off by default: a module can print anything. |
| `extensions` | query | `boolean` | no | Include the files installed extensions add, such as the log lines a printer sent, scrubbed. Off by default: the files come from code this server does not review. |

- credential: bearer token. The client method is `createDiagnosticsBundle`
- request body: `application/json` (`array of object`) or `application/octet-stream` (`binary`), required
- response `200`: The bundle, `application/zip` (`binary`)
- errors: `401`, `403`, `404`, `422`, `429`, `500`, each a [problem document](../../error-codes.md)

This operation has no sample: one zip archive, for the same reason a stored file is.
