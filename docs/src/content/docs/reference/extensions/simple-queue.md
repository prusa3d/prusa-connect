Print queue gives each printer a queue of print files. A person adds files from the printer or from storage, puts the files in the order they should print, and takes one off again. A file from storage picked on the Queue tab of a connected printer is copied to the printer at once and waits there. One added from the print dialog, or for a printer that is away, is sent when its turn comes. When the printer is free and its bed is clear, the next file starts. There is no planning across printers: a file waits in the queue it was put in.

A printer that finished a print still has the print on its bed, so the queue never starts the next file on it by itself. A file starts in one of three ways. A person presses Print next on the printer's Queue tab. A person adds a file to a printer that is ready. Or a person marks the printer ready, on its screen or with Set ready on the Queue tab.

The last way needs a grant. Installing the extension does not let it operate printers. A person who may share the printer turns on Let the queue start the next file by itself on its Queue tab. Until then a file starts only when a person starts it. Before the queue starts a file by itself, it checks that the person who added the file may still print on the printer and read the file. A file whose owner lost that right stays in the queue with a note saying why. A service account cannot add files to a queue.

Starting files by itself is reliable on a server with local accounts, where the install approved `check_absent_people`. The web install does that when an administrator approves the extension. There the server answers about every person at any time. A server with an OpenID Connect login or in open mode answers from the person's roles on this server. It answers only about a person who used the queue since the server or the extension last started. The files of anybody else wait for a person to press Print next, so there the queue does not reliably start files by itself. A person removed only at the login provider keeps their roles here, so take their role on the printer away too.

A printer marked ready belongs to the queue while the queue may start files by itself. A person who starts Print now on another file at that moment loses to it. Their file lands on the printer, and the printer refuses its start, because it already prints the queue's file. When the person's start reaches the printer first, the queue's start is refused. Its file goes back to the head of the queue with the note that the send failed.

A send that failed is not tried again by itself. The file goes back to the head of the queue with the reason, and waits for a person. The Print queue page shows every printer's queue one under another, on a timeline or as cards, as each person last chose. It links to the routes a script reaches the queues with in the API reference.

The README in `extensions/simple-queue` describes the routes, the settings and the gate.

## What it adds {#what-it-adds}

- **Print queue**: a page of its own, with an entry in the sidebar
- **Queue**: one line on each printer's card in the listing
- **Queue**: a tab of its own on each printer's page
- **Add to queue**: a section in the print dialog of a file in storage
- **Add to queue**: an item in the action menu of each file on a printer, for `.bgcode`, `.gcode`, `.gco`, `.g`
- **Add to queue**: a choice for a file dropped on a printer, run while it is copied there, for `.bgcode`, `.gcode`, `.gco`, `.g`

## Settings {#settings}

An operator writes them under `config:` in the extension's entry of the configuration.

| key | type | default | what it sets |
|---|---|---|---|
| `max_waiting` | int | `30` | How many files may wait in one printer's queue, from 1 to 60. |
| `keep_history` | int | `10` | How many ended prints each queue keeps, from 0 to 30. |
| `send_timeout` | string | `2h15m` | How long a file may be on its way to the printer before the queue gives it back, from 5m to 24h. |

## Routes {#routes}

Every path is under `/api/v1/modules/com.github.aux.prusa3d.simple-queue`. The extension's `openapi.json` describes each of them, and the server serves it at `openapi.json` under the same path.

| method and path | what it does |
|---|---|
| `GET /printers/{device}` | One printer's queue. |
| `POST /printers/{device}/entries` | Put a file on the queue. |
| `DELETE /printers/{device}/entries/{entry}` | Take a file off the queue. |
| `POST /printers/{device}/entries/{entry}/move` | Move a file in the queue. |
| `DELETE /printers/{device}/history` | Forget the ended prints. |
| `GET /printers/{device}/history` | One printer's ended prints. |
| `POST /printers/{device}/ready` | Mark the printer as ready, or not. |
| `POST /printers/{device}/start` | Print the next file now. |
| `GET /queues` | Every printer's queue, whole. |
